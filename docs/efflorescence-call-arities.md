# Efflorescence VM: 0・2・3引数のCALL特殊化実験（採用見送り）

2026-11-04、5種類の試作を比較した。
最終候補でも1・3引数のworker実行が約1.3%遅く、2引数のCLI全体も約2.1%遅い値となった。
「遅くならなければ」という採用条件を満たしたと判断できないため、実行コードを元に戻した。
現時点の製品コードは、従来の1引数特殊化と、0・複数引数の汎用ループを維持する。
ベンチマーク、回帰テスト、試作のパッチと測定データを残し、再検証できるようにした。

## 試作内容

最終候補では、flat実行器の引数搬送を小さな引数数に応じて処理した。

| 引数数 | 処理 |
| --- | --- |
| 0 | `CallSite#copy_arguments` からすぐに戻る。レジスタに触れない |
| 1 | 従来のまま、flat CALLの第4ワードに保持したソースから直接コピー |
| 2 | `CallSite#copy_arguments` で0・1番の引数を直接コピー |
| 3 | 同じ処理に2番の引数コピーを追加 |
| 4以上 | 従来の汎用ループ |

2・3引数の共通部分をまとめ、COPYごとにループ制御を行わない。
最後に明示的な `nil` を返すことで、Spinelの生成Cが最後のコピー値を不要な戻り値としてbox化するのを防ぐ。
ここでいうboxingはSpinel内部の汎用値表現であり、`Wardite::I32` の生成ではない。

VMのディスパッチ、フレーム取得・返却、Lowerer、命令幅4ワード、CALLの符号化は変更しない。
1引数のソースは0以上、それ以外は従来どおり第4ワードが `-1` となる。
CallSiteにキャッシュ用フィールドや、実行時の配列確保は追加しない。
オブジェクト形式のsemantic実行器は従来の引数ループを比較用に維持する。

## 比較した試作

最初は引数ソースをCallSiteの整数フィールドへキャッシュし、0引数を第4ワードの `-2` で区別してVMから搬送ヘルパーを呼ばない形にした。
100万回・seed 123・ウォームアップ1回後に3サンプルの探索的比較では、1引数が49.586→53.810 msと悪化した。
この試作では生成Cに、キャッシュのnil判定と、case式の不要な戻り値boxingもあった。

整数化と明示的なnil戻り値、VM側の追加判定の削除、キャッシュを使わないcase展開も比較したが、
1引数の悪化が残った。最終候補はキャッシュを持たず、直接コピーの共通部分をまとめた小さな実装とした。
これらは複数のコード生成上の差を含むため、特定の1要素だけを性能差の原因とは断定しない。
[5試作の全サンプル、元のfixture、8eb02afに対する各パッチ](../benchmark/results/call_arities_exploratory_2026-11-04.json)を保存している。

## 計測方法

`benchmark/i32_call_arities.wat` に、空ループと0〜4引数の呼び出しループを用意した。
比較する両版でインライン化を無効化し、CALL自体が残った状態で測る。

| export | 独立した期待値（mod 2³²） |
| --- | --- |
| empty_loop / call_one | seed |
| call_zero | seed + 7 × rounds |
| call_two | seed + rounds |
| call_three | seed + 3 × rounds |
| call_four | seed + 6 × rounds |

各引数数でWasmの演算内容も違うため、行同士の時間差を引数1個の費用とは解釈しない。
同じ行の改修前後を比較する。4引数は汎用経路、空ループと1引数は対照となる。
プロセスの実行順は交代させ、測定中のすべてのchecksumを独立参照計算と照合する。
0回・1回・32bit境界の入力も先に検証する。
命令数・レジスタ読み書き・関数への入場・フレーム生成のカウンタは別のプロセスで取得し、両版での一致を必須にしている。

## Spinelの本計測

macOS arm64、Spinel `2026.10.25+1967 (6e7fc1355)`、`-O2`、標準の整数overflowチェック。
5,000,000 rounds、seed 123、ウォームアップ2回後に7サンプル。
対照は `8eb02af` を独立してビルドしたもの。単位ms、平均 ± 標本標準偏差。

| export | 従来worker実行 | 試作worker実行 | 従来CLI全体 | 試作CLI全体 |
| --- | ---: | ---: | ---: | ---: |
| empty_loop | 93.003 ± 0.307 | 93.059 ± 0.368 | 99.496 ± 5.460 | 97.013 ± 0.321 |
| call_zero | 305.570 ± 18.836 | 296.973 ± 1.147 | 298.551 ± 1.138 | 297.015 ± 3.012 |
| call_one | 249.901 ± 2.397 | 253.043 ± 2.857 | 257.854 ± 1.102 | 268.603 ± 10.569 |
| call_two | 310.727 ± 2.299 | 310.535 ± 1.421 | 326.461 ± 1.980 | 333.368 ± 2.359 |
| call_three | 360.752 ± 1.337 | 365.347 ± 4.657 | 380.736 ± 1.243 | 381.954 ± 6.610 |
| call_four | 416.249 ± 7.010 | 406.585 ± 0.860 | 433.892 ± 1.697 | 418.432 ± 5.699 |

0引数は対照のばらつきが大きく、平均の差だけで安定した改善とは判断しない。
1・3引数のworker実行は約1.3%遅く、2引数はworkerで同等でもCLI全体では約2.1%遅い値だった。
4引数には改善する値も出ており、単純に引数コピーの命令数だけで説明できる結果ではない。
workerとCLIは別エントリポイントで、Spinelの生成コードも異なるため、両者の差を起動時間として差し引かない。
統計的な有意差は断定せず、今回の範囲では悪化しないことを確認できなかったと扱う。

すべてのchecksumと新旧MIRカウンタが一致した。
[全サンプル、実行条件、ソース・バイナリSHA256、最終候補のパッチ](../benchmark/results/call_arities_spinel_2026-11-04.json)を保存した。
パッチは後述の再実行モードで読み込み、コピーしたライブラリだけに適用する。

## 正しさと生成C

試作はCRubyとSpinelネイティブ版を含め、116テスト・10,891 assertionsが成功した。
実行コードを元に戻した後も全体を検証し、**116テスト・10,888 assertions、失敗・エラー・省略0件**。
どちらも `bundle exec rake check` と `-O2` のビルドが成功した。
既存の全受け入れ入力に加え、0〜4引数、void、引数の重複・順序変更、2・3引数の再帰、
ローカルの保持と再初期化、インライン化・フレーム再利用の無効化、semantic実行器、詳細計測を検証する。
新旧VMと独立参照計算を使って照合した。

試作の生成Cでは、2・3引数の固定位置への書き込み、不要な戻り値boxingがないこと、
整数レジスタ配列と具体的なFrame・CallSite・poolの型を確認する。
flat実行ループの多相呼び出しがないことも維持している。

## 再実行

```sh
CALL_ARITIES=1 CALL_ARITY_EXPERIMENT=1 BASELINE_REF=8eb02af SPINELFLAGS=-O2 RUNS=7 WARMUPS=2 \
  ruby benchmark/compare_call_types.rb 5000000 123

SPINELFLAGS=-O2 make spinel
WARDITE_SPINEL_BIN="$PWD/build/wardite" bundle exec rake test
bundle exec rake check
```

詳細な時間は `build/benchmark/call-arities/results.json` に保存する。
`CALL_ARITY_EXPERIMENT=1` は、保存したパッチを `build/` のコピーへ適用して試作を再現する。
適用前のパッチ検証と、ソース・コンパイラ設定・バイナリのSHA256確認を行う。
`rounds=10` のスモーク実行で、本計測と同じソースの再現と全checksumの一致を確認した。
この変数を省略すると、各コミットの製品コードをそのまま比較できる。
通常の `ruby benchmark/compare.rb` は従来の引数搬送を使う。
デフォルトのmixはインライン化で内部CALLが消えるため、引数搬送の調査には専用fixtureを使う。
