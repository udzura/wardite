# Efflorescence VM: 小さな関数のMIRインライン化

2026-11-04、短いleaf関数を展開する独立パスを追加した。
Spinel・`-O2` 固定の同一バイナリ比較で、`call_mix` の実行時間は **36.7%短縮**した。
これはCALLを除去する最適化の効果であり、残っているCALL/RETURN機構自体の高速化とは区別する。

## パイプラインと対象

```text
semantic MIR（保持）
  → 既存のローカルパス
  → Inlining（最適化済みモジュールのスナップショットを参照）
  → 変更した関数へ、有効なローカルパスを再適用
  → 定義前読み出しの検証 → Lowerer → VM
```

`Passes::Inlining` は関数名やベンチマークを判定しない。対象は次の条件を満たす関数に限定する。

- ローカルパス適用後で、末尾のRETURNを含めて8命令・32レジスタ以内。
- COPY、対応するi32演算、末尾のRETURNだけからなる直線状のleaf関数。
- 分岐、途中のRETURN、TRAP、内部CALL、計測命令、未知のopcodeは含まない。

展開前のスナップショットを1回だけ参照するため、内部CALLを展開した関数を次々に再展開しない。
再帰・相互再帰は通常のCALLのまま残る。
呼び出し元ごとの増加は、COPY整理前で最大64命令・256レジスタに制限する。
上限に達した呼び出し位置はCALLを維持する。

`--new-engine` ではデフォルトで有効。旧Stack VMのデフォルト動作は維持する。

```sh
# インライン化を無効化して、実際のCALL機構を比較する
build/wardite --new-engine --mir-disable inline --no-wasi \
  --invoke call_mix build/benchmark/i32_mix.wasm 100000 123

# 展開後の命令列と、詳細カウンタを確認する（時間測定とは別）
build/wardite --new-engine --mir-dump --mir-profile --no-wasi \
  --invoke call_mix build/benchmark/i32_mix.wasm 10 123
```

Ruby APIでは `disabled_optimizations: [:inline]` を指定できる。
`--mir-disable all` でも無効になり、他のパスも個別に切り替えられる。

## 引数・ローカル・戻り値

呼び出し先の引数、ローカル、一時値、定数を、呼び出し元の新しいレジスタへ割り当て直す。
引数をコピーしてから本体を実行するため、呼び出し先による引数の上書きは、呼び出し元の値を変更しない。
戻り値はCALLの格納先へコピーし、void関数では戻り値コピーを生成しない。
定数は書き換えない定数スロットとして複製し、即値オペランドはレジスタ番号へ変換しない。

非引数ローカルのゼロ初期化は、フレーム生成時ではなく、**展開した各呼び出し位置**に生成する。
同じ呼び出し位置がループで実行される場合も、前回の値を引き継がない。
`Rewrite` が分岐先を補正するため、CALLへの分岐も引数・ローカル初期化の先頭へ到達する。

既存のCOPY伝播に加え、同じ基本ブロック内で読み出される前に上書きされるCOPYを削除する。
これは後方の生存解析で判定し、ブロックの出口では全レジスタを使用されるものとして保守的に扱う。
`mix` では、最初の引数コピーは伝播後に不要になるが、後半の演算でも同じスロットを使うため、
従来の「関数全体で一度も読まれないCOPYだけを削除」では除去できなかった。

元の受け入れモジュール全体では、インライン化なしが20命令・37スロット、ありは23命令・49スロットになる。
元の`mix`関数や公開エクスポートも残す。レジスタの詰め直しは実装していない。
一方、`call_mix` の動的ディスパッチは `9 * rounds + 3` から `7 * rounds + 3` へ減り、
`inline_mix` と同じになる。

## Spinelでの比較

macOS arm64、Spinel `2026.10.25+1967 (6e7fc1355)`、`-O2`、標準の整数overflowチェック。
5,000,000 rounds、seed 123、ウォームアップ2回後に7回測定した。
表はworker内の `call_unboxed` 実行時間、単位ms、平均 ± 標本標準偏差。

| export | inline無効 | inline有効 | 実行時間の短縮 |
| --- | ---: | ---: | ---: |
| `empty_loop` | 92.825 ± 1.024 | 92.389 ± 1.994 | 差は小さい |
| `call_identity` | 247.971 ± 2.058 | **91.859 ± 0.572** | **63.0%** |
| `call_add_one` | 294.117 ± 2.881 | **128.647 ± 0.682** | **56.3%** |
| `inline_mix` | 279.717 ± 1.062 | 279.530 ± 1.656 | 差は小さい |
| `call_mix` | 439.907 ± 5.867 | **278.450 ± 1.498** | **36.7%** |

通常CLI全体でも、`call_mix` は **452.410 ± 2.773 → 286.044 ± 1.678 ms（36.8%短縮）**。
`inline_mix` は285.748 ± 2.229 → 285.901 ± 1.520 msで、改善を主張しない。
CLIとworkerは別々のエントリポイントであり、両者の差をそのまま起動時間とは解釈しない。

同一のネイティブCLIとworkerを、それぞれinline無効・有効で使っている。
処理順を交代し、各結果を独立した剰余演算の参照実装と照合した。mixのchecksumは `1647235310`。
0回・1回・負数ビットパターンの境界入力も測定前に検証する。
[全サンプル、設定、ソースとバイナリのSHA256](../benchmark/results/inlining_spinel_2026-11-04.json)を保存した。

### 通常のランタイム比較

`SPINELFLAGS=-O2 RUNS=5 WARMUPS=2 ruby benchmark/compare.rb` も実行した。
こちらはデフォルト入力の100,000 rounds・seed 123456789で、起動・ロード・変換を含むCLI全体を測る。
New VM / Spinelは `inline_mix` が **8.4 ± 0.3 ms**、`call_mix` が **8.3 ± 0.3 ms**だった。
全8構成のchecksumが参照計算と一致した。
[4ランタイム・両exportの全サンプルと実行条件](../benchmark/results/inlining_engines_2026-11-04.json)を保存した。
この比較でも、通常の `call_mix` にはインライン化が適用される。

### カウンタと変換コスト

詳細カウンタは別プロセスで取得し、通常の時間測定には入れない。
500万回の `call_mix` では次のようになった。

| 指標 | inline無効 | inline有効 |
| --- | ---: | ---: |
| 動的ディスパッチ | 45,000,003 | 35,000,003 |
| レジスタ読み出し | 40,000,003 | 30,000,003 |
| レジスタ書き込み | 35,000,001 | 25,000,001 |
| 関数への入場 | 5,000,001 | 1 |
| フレーム生成 | 2 | 1 |

対照用関数を追加した `i32_calls.wat` 全体では、静的MIRが46→48命令、74→92スロットになる。
同workerの `call_mix` 行で、ロードは0.108→0.118 ms、MIR変換・最適化・検証は0.196→0.252 msだった。
この小さな入力では変換時間は約0.056 ms増えた。大きな実アプリケーションでのコストは未測定。

## 正しさと生成Cの検証

Spinelネイティブ版を含む全体テストは **112 tests / 9,028 assertions、失敗・エラー・省略0件**。
`bundle exec rake check` と `-O2` のSpinelビルドも成功した。

元の受け入れWAT全体と8入力、各最適化の個別無効化に加え、引数の上書きとスナップショット、
複数引数、定数の戻り値、void呼び出し、ループ内のローカル初期化、展開位置への分岐、
サイズ上限・展開回数・新opcodeの対象外扱いを検証する。
再帰・相互再帰・再入の回帰テストも成功し、インライン化の有無の両方でI32の生成がRubyへの戻り値境界の1回だけであることを確認した。
生成Cの回帰テストでは、整数switch、整数レジスタ配列、具体的なFrame・pool・CallSiteの型、
flat実行ループの多相呼び出しがないことを維持している。

## 再実行

```sh
INLINE_ABLATION=1 SPINELFLAGS=-O2 RUNS=7 WARMUPS=2 \
  ruby benchmark/compare_call_types.rb 5000000 123

INLINE_ABLATION=1 RUNTIMES=CRuby,YJIT SPINELFLAGS=-O2 RUNS=3 WARMUPS=1 \
  ruby benchmark/compare_call_types.rb 100000 123

SPINELFLAGS=-O2 make spinel
WARDITE_SPINEL_BIN="$PWD/build/wardite" bundle exec rake test
bundle exec rake check
```

同一バイナリ比較の結果は `build/benchmark/inlining/results.json` に保存する。
通常の `ruby benchmark/compare.rb` にも、このインライン化は反映される。
過去のCALL機構の比較を維持するため、`INLINE_ABLATION` を指定しない `compare_call_types.rb` と
`investigate_calls.rb` は、対応する版ではインライン化を明示的に無効化する。
通常のコミット比較では、MIRカウンタの一致条件も維持している。

## 制約と次の候補

分岐・再帰・内部CALLを含む関数は展開しないため、そのような実アプリケーションのCALL負担は残る。
今回の閾値は保守的な初期値であり、実アプリの命令数・呼び出し頻度・変換時間を計測して調整する余地がある。
次の候補は、未使用レジスタと定数スロットの整理、書き込みがない引数スロットの直接対応付け、
より広い関数を対象にしたコストモデル。分岐を持つ関数の展開には制御フローと早期RETURNの変換が別途必要になる。
