# Efflorescence VM: フレーム再利用時の初期化を軽量化する

2026-11-04、[callコストの調査](efflorescence-call-investigation.md)に基づき、フレーム再利用時の初期化範囲を絞った。
Spinelでの `call_mix` は、全レジスタ初期化の対照に比べて約17%短縮した。

## 初期化する範囲

| 領域 | フレーム生成時 | 再利用時 |
| --- | --- | --- |
| 引数 | テンプレートを複製した後、呼び出し元が設定する | 呼び出し元がすべて上書きする |
| 非引数ローカル | テンプレートから0を設定する | この範囲だけ0に戻す |
| 定数 | テンプレートから設定する | 保持する |
| 一時レジスタ | テンプレートを複製する | 使用前に命令が書き込む |
| PC・戻り値の格納先 | 呼び出しの情報を設定する | 呼び出しの情報を設定する |

`Frame.new` は `initial_registers.dup` で整数配列を生成する。以前の「全スロットを0で確保してから、Rubyのループで全初期値を上書きする」二重の処理も省いた。

`Frame#reset` は、Frame生成時に保存したローカル範囲だけを走査する。非引数ローカルがないmixなどのcalleeでは、レジスタへの書き込みは発生しない。レジスタ番号の詰め直しやMIR命令の追加・融合は行っていない。

## 一時レジスタを残しても安全であることの確認

新しい `RegisterValidation` が、最適化後のMIRをロード時に検証する。タイミングはPROFILE命令の挿入・フラット化より前であり、通常実行・カウンタ計測・各最適化を無効にした場合のすべてに適用する。

1. 関数の入口では、引数・ローカル・定数だけを定義済みとする。
2. Basic Block内を順番に読み、ソースは定義済みであることを確認し、命令の書き込み先を定義済みにする。
3. 分岐先と継続先へ定義情報を伝える。合流点では、到達した全経路の情報の共通部分を取る。
4. 合流点の情報が変わった場合は、そのブロックを再検証する。ループのバックエッジによって、初回入口には存在しない定義を認めることはない。
5. 定義前の読み出しや、定数スロットへの書き込みは `TranslationError` にする。

状態は命令ごとではなくBasic Blockごとに持つ。フラグは整数配列で表現し、ネイティブ整数幅を超えるビットマスクに依存しない。実行ループ内での検証・条件追加・allocationはない。

フレームpoolは従来どおり公開APIの1回の呼び出しごとに独立させる。実行中の再帰フレームは空き一覧に戻さず、同じVMへの再入・重なり合う呼び出しでもレジスタを共有しない。trapで中断した呼び出しのpoolを次の公開呼び出しへ持ち越すこともない。

## 性能測定

CRuby 4.0.9、Spinel `2026.10.25+1967 (6e7fc1355)`、macOS arm64。
ネイティブバイナリは `-O2` と通常の整数overflowチェックを使う。
seed 123、5,000,000 rounds、2回のウォームアップ後に7回測定した。表は平均 ± 標本標準偏差、単位はms。

| export | 全レジスタ初期化 | ローカルのみ初期化 |
| --- | ---: | ---: |
| `inline_mix` | 325.463 ± 2.453 | 327.028 ± 2.406 |
| `call_mix` | 727.817 ± 15.768 | **603.672 ± 13.384** |

`call_mix` は実行時間が **17.1%減少**した。`inline_mix` では測定のばらつきと同程度の差だった。
全測定で両exportのchecksumは `1647235310` と一致した。MIRの動的命令数も両版で一致し、inlineは35,000,003、callは45,000,003だった。

対照の `full_reset` は、現在のライブラリをコピーして `Frame#reset` のループだけを全スロット初期化へ戻したもの。
新規Frameのテンプレート複製、ロード時の定義解析、MIR、エントリポイント、コンパイラ設定は両版で同じにする。
したがって、今回の比較は再利用時の初期化範囲の効果であり、新規Frame生成の改善分を含まない。

測定は1サンプルにつき1プロセス。ロード・MIR生成と実行時間を分け、実行には `call_unboxed` の準備・フレーム設定を含める。
詳細カウンタとallocationは別プロセスで取得し、時間測定には含めない。実行順序は回転・反転する。

最初に100万回・全30構成で探索的に測定したが、call_mixに大きなばらつきがあったため、上記の長い比較で確認した。
[主測定の全サンプル・ソースとバイナリのSHA256](../benchmark/results/selective_reset_spinel_2026-11-04.json)と、
[探索的な30構成のデータ](../benchmark/results/selective_reset_spinel_2026-11-04_exploratory.json)を保存している。

```sh
# 主測定と同じ条件
VARIANTS=full_reset,locals_only EXPORTS=inline_mix,call_mix \
  RUNS=7 WARMUPS=2 ruby benchmark/investigate_calls.rb 5000000 123

# ループ・identity・add_one・mix、allocation方式も含めた全30構成
RUNS=7 WARMUPS=2 ruby benchmark/investigate_calls.rb 1000000 123
```

## 検証

CRuby・Spinelのネイティブテストを含む全体で、**95 tests / 5,009 assertions、失敗・エラー・省略0**。
`bundle exec rake check` とSpinelビルドも成功した。

追加テストでは、片方の分岐にしか代入がないMIR、後から到達した経路によって定義が失われる合流点、初回未定義のループ、到達不能コード、定数への書き込みを検証する。
Wasm実行では、2個の非引数ローカルの再初期化、分岐結果、一時値、即値化を無効にした定数参照、再帰中の生きたローカル、同期的な再入、trap後の再実行を確認する。
64個を超えるレジスタと、元の受け入れベンチマーク全体も実行している。
