# ADR 0030: MIR2 キャッシュキーの SHA-256 を Spinel の Arm SHA2 命令で高速化する

- **状態** 採用。Spinel のパッチ済みリビジョンを Wardite の CI・リリースビルドに固定する。
- **日付** 2026-11-22

## 背景

[ADR 0009](0009-efflorescence-mir2-cache-integrity-modes.md) の MIR2 キャッシュは、元の Wasm 全体の SHA-256 をキーに含める。同じパスの Wasm が変更されたときは別のキーを引く。[ADR 0029](0029-efflorescence-spinel-interpreter-costs.md) では、Ruby 4.0.9 の MIR2 と起動スナップショットが両方ヒットした場合も、プロセス起動から終了まで 147.65 ms かかった。

Wardite #89 の Ruby 4.0.9 を同じ条件で32回ずつ起動したところ、計測ビルドの中央値は 147.36 ms、無改変ビルドは 147.32 ms だった。MIR2 のキー生成・読み込み・関数の遅延復元に 79.51 ms かかり、そのうち元の Wasm の SHA-256 を含むキー生成が 47.37 ms を占めた。遅延復元を各区間から差し引くと、スナップショットの復元は 44.39 ms、復元後の Ruby の実行は 0.11 ms だった。このスナップショットでは Ruby がバージョンを出力する直前の WASI 呼び出しから再開する。[計測パッチと全サンプル](https://github.com/udzura/wardite-benches/pull/11)

## 決定

Wardite はキーを引く前に元の Wasm 全体をハッシュする。Spinel の SHA-256 ブロック圧縮で、リトルエンディアンの AArch64 コンパイル対象が SHA2 と NEON に対応する場合に Arm SHA2 命令を使う。汎用 AArch64 と `SP_PORTABLE` は従来の C 実装、x86-64 は既存の CPUID による実行時選択を使う。[Spinel #12380](https://github.com/matz/spinel/pull/12380)

Wardite は CI と Zig リリースビルドの Spinel を #12380 のパッチ済みコミット `a6454297079f25e7d1d4d0d094ffdd45b3d9ac0b` に固定する。upstream へのマージ後は、その変更を含むリビジョンに両方のピンを更新できる。問題があれば両方を #89 の `68476ebd3` に戻す。ダイジェストとキャッシュ形式は互換であり、切り戻し時にも同じ MIR2 とスナップショットを再利用できる。

## 比較検証

Apple M3 Pro で Wardite を同じ `3edaf5d` に固定し、Spinel `f341ce1bf` と、そこに Arm SHA2 の変更だけを加えた `954dc004b` を比較した。両ビルドで変更前に作った MIR2 と起動スナップショットを共有し、Wasm のハッシュと Ruby の出力を照合した。[検証コードと全サンプル](https://github.com/udzura/wardite-benches/pull/12)

| 区間（中央値） | 変更前 | Arm SHA2 |
|---|---:|---:|
| 読み込み済み Wasm 21,444,697 B の SHA-256（各64回） | 48.24 ms | 9.09 ms |
| 全キャッシュから Ruby を実行する新規プロセス全体（各32回） | 147.12 ms | 92.39 ms |

## 生成済みモジュールを直接ロードする

`wardite --compile-wmir ruby.wmir -- ruby.wasm` は元の Wasm を一度読み、同じバイト列から SHA-256 と全関数の MIR を生成する。生成中は import の型と関数索引を使い、ゲストの start 関数とホスト関数の実行はロード時まで保留する。同一ディレクトリに一時ファイルを書き、close 後に rename して公開する。

`wardite -- ruby.wmir …` は成果物を読み取り専用で mmap し、元の Wasm のパスとキャッシュディレクトリの探索を省く。WASI、メモリ、テーブル、グローバル、ホスト関数はロードごとに初期化する。`--snapshot DIR` には通常の Wasm と同じ MIR2 キーが渡るので、ゲスト引数、環境、WASI の設定が一致すれば既存のスナップショットから再開できる。

### ファイル形式と検証

バージョン 1 の配置は固定長ヘッダ、MIR2 ペイロード、元の Wasm の順。整数はリトルエンディアンとする。

| オフセット | 内容 |
|---:|---|
| 0 | マジック `WARDWMIR`（8 B） |
| 8 | WMIR 版、MIR2 形式版、MIR コード版、有効化した最適化のビットマスク、関数ディレクトリ長、MIR2 ペイロード長、Wasm 長（各 u32） |
| 36 | Wasm の SHA-256、通常の MIR2 キー、MIR2 ペイロードの SHA-256（各32 B） |
| 132 | 先頭132 B と関数ディレクトリを連結した値の SHA-256（32 B） |
| 164 | 関数ディレクトリとレコードを含む MIR2 ペイロード。その直後が Wasm |

既定ではヘッダと関数ディレクトリを検証し、各レコードの範囲、署名、ローカル宣言と復元時の命令検証を既存の MIR2 デコーダに通す。呼び出す関数のレコードだけをマッピングから取り出す。Wasm のコードセクションではローカル宣言と命令列の位置を読み、命令列の読み出しは元の Wasm を検査する API が必要とするまで遅延する。カスタムセクションは seek で飛ばす。

成果物は信頼する生成元から入手し、マッピング中の inode へ上書きしない。`--mir-cache-verify sha256` を指定すると、ロード前に埋め込み Wasm と MIR2 ペイロードの全域をヘッダのダイジェストと照合する。どちらのモードでも不整合や非対応のバージョンはエラーにする。CRuby と Spinel はそれぞれの MIR2 キーを使うため、成果物の生成と実行には同じエンジンを使う。切り戻す場合は元の `.wasm` と従来の `--mir-cache` を指定する。

### Ruby 4.0.9 の直接起動

Apple M3 Pro（macOS 27.2.1 arm64）、Spinel `a64542970`、Wardite `fe4457e` の同じバイナリで、OS のファイルキャッシュを温めた後、新規プロセスを各15回起動した。ゲスト引数は `--disable-gems -e 'puts RUBY_DESCRIPTION'`。21,444,697 B の Wasm から 112,245,440 B の WMIR を生成するのに 4.05 秒（1回）かかった。生成とキャッシュの準備は表の計時外。[検証コードと全75回の測定値](https://github.com/udzura/wardite-benches/pull/13)

| 起動条件 | 終了までの中央値 |
|---|---:|
| Wasm、オプションなし | 2,204.33 ms |
| Wasm、MIR2 ヒット | 527.69 ms |
| WMIR を直接指定 | 493.66 ms |
| Wasm、MIR2 とスナップショットがヒット | 98.18 ms |
| WMIR を直接指定、同じスナップショットがヒット | 66.79 ms |

MIR2 がヒットする Wasm と比較すると、直接ロードはスナップショットなしで 34.04 ms（6.5%）、同じスナップショットからの再開で 31.40 ms（32.0%）短縮した。

### スナップショット復元と MIR 宣言の起動コストを減らす

Ruby 4.0.9 のスナップショットでは、線形メモリが 314 ページから 4,857 ページに拡張され、119 ページに保存データがある。従来は保存対象外の 4,738 ページをすべてゼロで上書きしていた。復元では次の順に変更を適用する。

1. 保存されていないページのうち、拡張前から存在したページだけをゼロクリアする。ここには Wasm の初期データが残り得る。新規ページのゼロ初期化はメモリ拡張が保証する。
2. Spinel で復元時に拡張が必要なら、検証済みのページ数に合わせてゼロ初期化済みバッファを確保する。保存ページを直接書き戻すことで、古いバッファのコピーを省く。ページ数の上限、ロック、確保の成功を確認してから切り替える。
3. MIR 関数ディレクトリのオフセットと長さを一括で読み、モジュールの型ごとに符号化した署名を再利用してレイアウトを照合する。
4. active data セグメントのオフセット式は、`i32.const`、符号付き LEB32、`end` を一度で読む。この Ruby Wasm では 5,649 個の式で汎用命令デコーダによる再読を省ける。
5. MIR 関数ごとの命令列、バイトコード、例外ハンドラなどの空配列を、最初の利用時に確保する。直接呼び出しの解決先テーブルは、Spinel が命令ループで専用のポインタ配列を使えるよう、関数の宣言時に確保する。未実行関数を宣言しただけでは確保せず、呼び出し側には従来どおり関数ごとに独立した可変配列を返す。

Apple M3 Pro、Spinel `a64542970`、`-O2` で #92 と #93 を併用した。OS のファイルキャッシュを温め、同じ Ruby 4.0.9 と引数 `--disable-gems -e 'puts RUBY_DESCRIPTION'` で、新規プロセスの起動から終了までを比較した。Wardite は同一の WMIR とスナップショットを共有し、Wasmtime 51.0.0 は同じ Wasm を事前コンパイルした cwasm を直接起動した。各系列内で実行順を交替し、以下に各32回の中央値を示す。[検証コードと生データ](https://github.com/udzura/wardite-benches/pull/14)

| 計測系列 | 同一系列で比較した条件 | 終了までの中央値 |
|---|---|---:|
| ゼロクリア | 変更前 → 変更1 | 67.31 → 49.85 ms |
| 段階別 | 変更1 → ＋新規バッファ → ＋ディレクトリ → ＋data オフセット | 49.19 → 47.20 → 47.18 → 41.04 ms |
| 最終比較 | 変更1 → 全5変更（試作） | 77.06 → 60.15 ms |
| 最終比較 | 関数ディレクトリ変更のみを外した試作 | 66.42 ms |
| 最終比較 | Wasmtime の cwasm | 48.56 ms |

最終比較で Wardite は **16.91 ms（21.9%）短縮**し、起動時間は同じ系列の Wasmtime の **1.24 倍**だった。最終比較時には macOS の低電力モードが有効で、前半の電力設定は記録していない。ADR 0029 の Wasmtime 30.85 ms にこの比率を当てはめると約 38.2 ms になるが、この系列から以前の条件での 39 ms 到達は確認できない。[最終比較の全サンプル](https://github.com/udzura/wardite-benches/blob/e402b46/benchmark/wmir/phases/prepared-startup/m3-pro.json)

data セグメント走査と MIR 命令検証の C FFI は、同じ親ビルドとの比較で起動を短縮できず、採用を見送った。4 MiB Base64 decode は変更1と全5変更の比較で 289.30 → 291.52 ms（各8回の中央値、+0.8%）。全回の復号結果の SHA-256 が一致した。[段階別の試作と Base64 の結果](https://github.com/udzura/wardite-benches/tree/e402b46/benchmark/wmir/phases/prepared-startup)

### Wardite 本体に取り込んだ版での再計測

実装の先端 `05e8170` を、上の試作と同じ Spinel `a64542970` で `-O2` ビルドした。直接呼び出し先テーブルのネイティブ表現を保つ修正を含む。中間段階は再ビルドせず、以前に保存した2つの対照バイナリと Wasmtime 51.0.0 を加えて交互に起動した。4条件で標準出力は一致し、Wardite の各版で WMIR のマッピングとスナップショット復元を確認した。計測前後とも macOS の低電力モードは有効だった。[計測コマンド、入力・バイナリの SHA-256、全128サンプル](https://github.com/udzura/wardite-benches/blob/288f2db8d7c855860ab0545f92b1e841eb9bef2f/benchmark/wmir/phases/prepared-startup/wardite-pr-stack.json)

| 準備済み成果物からの起動 | 各32回の中央値 |
|---|---:|
| Wardite #92＋#93、ゼロクリア変更前 | 107.62 ms |
| Wardite、ゼロクリア変更のみ | 79.87 ms |
| Wardite、全変更入り | **63.66 ms** |
| Wasmtime 51.0.0、cwasm | **50.78 ms** |

全変更入りは変更前から 43.97 ms（40.9%）、ゼロクリア変更のみの版から 16.21 ms（20.3%）短縮した。同時に測った Wasmtime の 1.25 倍で、差は 12.88 ms だった。

### 電力モード別の最終計測

全変更入り Wardite の WMIR＋スナップショットと Wasmtime 51.0.0 の cwasm の2条件だけで再計測した。低電力モード OFF の初回は各32回の中央値が **37.332 ms / 29.037 ms**、手元での再現は **35.194 ms / 27.893 ms** で、いずれも Wardite の起動が目標の 39 ms を下回った。同じ手順で低電力モードを ON にした手元の結果は **59.529 ms / 45.995 ms** だった。今後は macOS の電力モードを計測前後に記録し、同じモードで測った結果を比較する。[電力モード別の中央値と生データ](https://github.com/udzura/wardite-benches/tree/9a0265e3d15ce9766abad8904a68a17df2166ce6/benchmark/wmir/phases/prepared-startup)
