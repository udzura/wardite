# ADR 0008: Efflorescenceのruby.wasm対応フェーズ2

- **状態** 提案
- **日付** 2026-11-11
- **前提** [ruby.wasm対応フェーズ1](0007-efflorescence-ruby-wasm-phase1.md)

## 決定

フェーズ1と同じRuby 4.0.9のWasmで、MIR2ビルド結果の再利用と、ゲスト実行中に残るVMの費用を順に改善する。MIR2は検証とloweringを終えたフラット命令列および実行に必要なメタデータを指す。キャッシュはCRubyホストのEfflorescenceで明示的に有効化する。RubyGemsを含む配布構成、Spinelへのキャッシュ移植、新しいWasm機能、WASI全APIは対象外とする。

調査では、YJIT有効でWasmのロード開始から実行直前までが、新規MIRビルドの約15.3秒から別プロセスでのキャッシュ再利用時に約4.6秒になった。新規ビルドの値は保存時間を除く。試作データは約65 MBで、保存約2.4秒、読み戻し約2.9秒。Wasmデコードとインスタンス構築はキャッシュ再利用時も行った。ゲスト実行は `memory.fill` 改善後に約9.5秒だった。各値は試作の単発計測で、フェーズ1の実装後に基準を取り直す。

## 5. MIR2ビルドキャッシュ

### キャッシュ対象

[VMの初期化](../../lib/wardite/efflorescence/vm.rb) ではMIR変換、最適化、レジスタ検証、loweringの順に行う。キャッシュには最後まで成功した関数のフラット命令、初期レジスタ、呼び出し先や例外・メモリ命令の参照表、シグネチャを保存する。関数への参照は関数index等の整数で保持し、読み戻すときに解決する。数値定数はi64の符号とf32/f64のビット列を復元できる表現にする。

Wasmのデコード、モジュール構成とimportの確認、Store・メモリ・table・globalの初期化は毎回行う。WASIのcallableは当該インスタンスのimportから解決し、`start` セクションの関数とCLIが呼ぶ `_start` の順序を維持する。ホストオブジェクト、WASIの状態、フレーム、実行後のメモリは保存しない。`--mir-dump` と `--mir-profile` は、必要な中間表現を生成する通常のビルド経路を使う。

### キー、形式、書き込み

- CLIからローカルのキャッシュディレクトリを明示できるようにする。キーはWasm全体のSHA-256、MIR2形式と生成コードの互換バージョン、正規化したMIR最適化設定から作る。opcodeやメタデータの意味が変わる場合は互換バージョンを更新する。
- バージョン付きのデータ形式を定義し、Rubyの `Marshal` は使わない。読み取り時にサイズ、個数、index、opcode、コード幅と分岐先を確認し、元のモジュールと関数・importの構成を照合する。検証済みの結果を再利用するため、キャッシュの信頼境界は実行ユーザーが管理するローカルディレクトリとする。共有ディレクトリや外部配布のキャッシュは対象外とする。
- 形式不一致・破損・読み取り失敗はキャッシュミスとして扱う。保存は同じディレクトリに一時ファイルを書いてからrenameし、他プロセスに中途半端な内容を見せない。キャッシュに書けなくても、ビルドが成功していれば通常どおり実行する。

### 検証

同一Wasmを別プロセスで起動してヒットを確認し、`-e` と `require_relative` の標準出力・終了コード、startの副作用、trapと例外処理をキャッシュなしの実行と照合する。異なるホストcallableでの再リンクと、インスタンス間でメモリ・globalが独立することを確認する。Wasm、互換バージョン、最適化設定の変更、切り詰め・不正index、同時書き込みと書き込み不可も試験する。

キャッシュ無効、ミスして保存、別プロセスでヒットの3通りで複数回計測する。Wasmデコード、MIR2生成、読み書き、Store初期化、実行の各時間と、キャッシュサイズ・ピークRSSを記録する。ファイルが既にOSのキャッシュに載っている測定は、その条件を記録する。

## 6. ゲスト実行時間の改善

フェーズ1の `memory.fill` とフェーズ2のキャッシュを適用した状態で、`_start` 以降だけをサンプリングする。試作ではfillの改善後に `execute_flat` と `Array#fetch` が上位に残った。まず命令の内訳と呼び出し元を調べ、ディスパッチ、オペランド参照、メモリ処理のどれが費用を占めるか切り分ける。WASI呼び出しは元の `-e` 計測で15回・合計約0.4 msだったため、新しいWASI専用経路は計測で必要性が出た場合に検討する。

上位の経路を独立した変更で比較する。境界検査、trapの位置と副作用、フレームと例外の契約を維持する。サンプリングと実時間計測を分け、同じRubyのWasmと出力を使い、計測用profilingを無効にして複数回実行する。既存のi32・i64・float、call、Storeのベンチマークで小さなモジュールへの影響も調べる。効果を再現できる変更を採用し、次に調べる経路は改善後のプロファイルで決める。

## 受け入れ条件

フェーズ1のRuby 4.0.9受け入れケースを維持し、同一Wasmの再起動でロード開始から実行直前までの短縮を確認する。ゲスト実行の改善はキャッシュの読み書きと分けて示す。CRubyのtest・型チェック・parityと、共有VMを変更した場合はSpinel回帰を実行する。
