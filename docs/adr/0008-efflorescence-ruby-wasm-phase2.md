# ADR 0008: Efflorescenceのruby.wasm対応フェーズ2

- **状態** 提案
- **日付** 2026-11-11
- **前提** [ruby.wasm対応フェーズ1](0007-efflorescence-ruby-wasm-phase1.md)

## 決定

フェーズ1と同じRuby 4.0.9のWasmで、MIR2ビルド結果の再利用、Spinel版の線形メモリの置き換え、残るゲスト実行時間の改善をこの順で進める。MIR2は検証とloweringを終えたフラット命令列および実行に必要なメタデータを指す。キャッシュはCRubyホストのEfflorescenceで明示的に有効化する。RubyGemsを含む配布構成、Spinelへのキャッシュ移植、新しいWasm機能、WASI全APIは対象外とする。

調査では、YJIT有効でWasmのロード開始から実行直前までが、新規MIRビルドの約15.3秒から別プロセスでのキャッシュ再利用時に約4.6秒になった。新規ビルドの値は保存時間を除く。試作データは約65 MBで、保存約2.4秒、読み戻し約2.9秒。Wasmデコードとインスタンス構築はキャッシュ再利用時も行った。ゲスト実行は `memory.fill` 改善後に約9.5秒だった。各値は試作の単発計測で、フェーズ1の実装後に基準を取り直す。

## 5. MIR2ビルドキャッシュ

### キャッシュ対象

[VMの初期化](../../lib/wardite/efflorescence/vm.rb) ではMIR変換、最適化、レジスタ検証、loweringの順に行う。キャッシュには最後まで成功した関数のフラット命令、初期レジスタ、呼び出し先や例外・メモリ命令の参照表、シグネチャを保存する。関数への参照は関数index等の整数で保持し、読み戻すときに解決する。数値定数はi64の符号とf32/f64のビット列を復元できる表現にする。

Wasmのデコード、モジュール構成とimportの確認、Store・メモリ・table・globalの初期化は毎回行う。WASIのcallableは当該インスタンスのimportから解決し、`start` セクションの関数とCLIが呼ぶ `_start` の順序を維持する。ホストオブジェクト、WASIの状態、フレーム、実行後のメモリは保存しない。`--mir-dump` と `--mir-profile` は、必要な中間表現を生成する通常のビルド経路を使う。

### キー、形式、書き込み

- CLIからローカルのキャッシュディレクトリを明示できるようにする。キーはWasm全体のSHA-256、MIR2形式と生成コードの互換バージョン、正規化したMIR最適化設定から作る。opcodeやメタデータの意味が変わる場合は互換バージョンを更新する。
- バージョン付きのデータ形式を定義し、Rubyの `Marshal` は使わない。読み取り時にサイズ、個数、index、opcode、コード幅と分岐先を確認し、元のモジュールと関数・importの構成を照合する。検証済みの結果を再利用するため、キャッシュの信頼境界は実行ユーザーが管理するローカルディレクトリとする。共有ディレクトリや外部配布のキャッシュは対象外とする。
- 形式不一致・破損・読み取り失敗はキャッシュミスとして扱う。保存は同じディレクトリに一時ファイルを書いてからrenameし、他プロセスに中途半端な内容を見せない。キャッシュに書けなくても、ビルドが成功していれば通常どおり実行する。

### 検証

同一Wasmを別プロセスで起動してヒットを確認し、`-e` と `require_relative` の標準出力・終了コード、startの副作用、trapと例外処理をキャッシュなしの実行と照合する。異なるホストcallableでの再リンクと、インスタンス間でメモリ・globalが独立することを確認する。Wasm、互換バージョン、最適化設定の変更、切り詰め・不正index、同時書き込みと書き込み不可も試験する。

キャッシュ無効、ミスして保存、別プロセスでヒットの3通りで複数回計測する。Wasmデコード、MIR2生成、読み書き、Store初期化、実行の各時間と、キャッシュサイズ・ピークRSSを記録する。ファイルが既にOSのキャッシュに載っている測定は、その条件を記録する。

## 6. Spinel版の線形メモリをIO::Bufferに移行

Ruby 4.0.9の起動では256 MiBの `memory.fill` が1回あり、Spinel版Warditeの1バイトずつの書き込みに約0.54秒かかった。Spinelの `IO::Buffer#clear(value, offset, length)` は範囲検査後に `memset` を呼ぶ。確保・初期化済みの256 MiBのバッファを埋める単体計測では約5 msだった。ゲストの起動時間とは別に計測する。

### 6a. Spinelに書き込み可能なStringビューを実装

Spinel側で `IO::Buffer.for(string) { |buffer| ... }` を実装し、CRuby 4.0.9の契約と照合する。可変のStringにはコピーを伴わない書き込み可能なビューを渡し、凍結されたStringのビューは読み取り専用にする。ブロック実行中はStringの領域と寿命を保護し、正常終了と例外の双方でロックを解除して、ブロックに渡したバッファを解放する。Warditeではビューと派生スライスをブロック内で使い切る。ブロックの戻り値、元のStringへの書き戻し、範囲外・読み取り専用での拒否も検証する。 [Ruby 4.0のIO::Buffer](https://docs.ruby-lang.org/en/4.0/IO/Buffer.html#method-c-for)

Warditeではこのブロック形式を使い、現行のStringをバックエンドとするSpinel版で `memory.fill` を `buffer.clear` に置き換えて効果を測る。ここでの `IO::Buffer.for` は既存Stringを借りる移行用の経路で、線形メモリの所有権を移すのは6bとする。

### 6b. Warditeの線形メモリを所有バッファに置き換える

Spinel版の [Memory](../../lib/wardite.rb) が `IO::Buffer` を直接所有する。Storeのアクティブデータ配置、両VMの既存load/storeとbulk memory、`memory.grow`、[WASIの読み書き](../../lib/wardite/wasi.rb) を同じバッファに接続し、`memory.fill` は範囲検査後に `buffer.clear` を呼ぶ。CRuby版の既存String APIを維持する。Spinel版のホスト境界ではバッファへのアクセスを明示し、Stringが必要なI/Oでは対象範囲だけを変換する。ホストコールバックからの読み書きと、APIの型・互換性の差を実装記録に残す。

メモリの範囲外trapと副作用の順序、little-endianの値、`memory.copy` の重複、`memory.grow` 成功時のゼロ初期化と失敗時の状態保持を確認する。growをまたいで古いバッファやビューを再利用しない。通常のload/storeとWASIの小さな読み書きも計測し、バッファへの移行で生じる退行を確認する。

CRuby版・Spinel版でフェーズ1の `-e`、`require_relative`、`exit 7` をWasmtimeと照合する。Spinel版は、現行のバイトループ、6aのStringビュー、6bの所有バッファで同じWasmを実行し、256 MiBのfillと `_start` 全体を分けて比較する。

## 7. ゲスト実行時間の改善

CRuby版はMIR2キャッシュ、Spinel版は所有バッファを適用した状態で、`_start` 以降だけをサンプリングする。CRuby版の試作ではfillの改善後に `execute_flat` と `Array#fetch` が上位に残った。まず命令の内訳と呼び出し元を調べ、ディスパッチ、オペランド参照、メモリ処理のどれが費用を占めるか切り分ける。WASI呼び出しは元の `-e` 計測で15回・合計約0.4 msだったため、新しいWASI専用経路は計測で必要性が出た場合に検討する。

上位の経路を独立した変更で比較する。境界検査、trapの位置と副作用、フレームと例外の契約を維持する。サンプリングと実時間計測を分け、同じRubyのWasmと出力を使い、計測用profilingを無効にして複数回実行する。既存のi32・i64・float、call、Storeのベンチマークで小さなモジュールへの影響も調べる。効果を再現できる変更を採用し、次に調べる経路は改善後のプロファイルで決める。

## 実装順とコミット

各行を独立したコミットにし、対応する回帰試験、計測結果、必要なRBSを含める。6aのSpinel実装とWarditeからの利用は各リポジトリでコミットし、Warditeの検証では対応するSpinelのリビジョンを固定する。Warditeのコミットメッセージには `Co-authored-by: Codex <codex@openai.com>` を付ける。

## 受け入れ条件

フェーズ1のRuby 4.0.9受け入れケースを維持し、CRuby版では同一Wasmの再起動でロード開始から実行直前までの短縮を確認する。Spinel版では所有バッファでfillの高速化を確認する。ゲスト実行の改善はキャッシュの読み書きと分けて示す。CRubyのtest・型チェック・parityとSpinel回帰を実行する。
