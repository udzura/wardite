# ADR 0012: Efflorescenceの起動スナップショット

- **状態** 採用。実装順1〜6を実装・検証済み。[実装・検証・性能記録](../efflorescence-startup-snapshot.md)を参照。
- **日付** 2026-11-12
- **前提** [ruby.wasm対応フェーズ2](0008-efflorescence-ruby-wasm-phase2.md)、[MIR2キャッシュの実装記録](../efflorescence-mir2-cache.md)

## 背景

Spinel版でRuby 4.0.9のWasmをMIR2キャッシュのヒットで起動すると約1.5秒かかり、うち約半分がゲスト実行である（`-e 'puts RUBY_DESCRIPTION'`、1回のプロファイルで1151サンプル中743）。このスクリプトではゲスト実行のほとんどがRuby VMの初期化にあたる。

初期化後の状態を保存して次回の起動で復元できれば、初期化の実行を省ける。このADRは、ゲストのWasmを変更せずにWardite側だけで行う方式を定める。

この方式はRubyに固有ではない。チェックポイントの位置を関数名ではなくWASIの呼び出しの種類で決めるため、WASI Preview 1を使うWasmであれば同じ仕組みで動く。Rubyに固有なのは、以下の調査結果、効果の見積もり、検証ケースである。

### 調査で確認した事実

- Rubyの起動順序は `_start` → wasi-libcの `__main_void`（引数の取得）→ `main` → `ruby_sysinit` → `rb_wasm_rt_start(rb_main)` → `ruby_init` → `ruby_options(argc, argv)` → `ruby_run_node`（`main.c`、`wasm/runtime.c`）。
- 検証に使うWasmのexportは `memory`、`_start`、`asyncify_*` の7個で、初期化だけを行う関数はexportされていない。nameセクションもなく、関数名から位置を決められない。
- メモリは初期271ページ、tableは3477要素のfuncref、globalは可変のi32が3個。
- EfflorescenceのWasm間の呼び出しはホストのスタックを使わない。[Frame](../../lib/wardite/efflorescence/ir.rb) の配列で管理し、各フレームは関数、`pc`、整数のレジスタ配列、ハンドラの深さ、戻り先レジスタを持つ。
- [execute_flat](../../lib/wardite/efflorescence/vm.rb) の `CALL_HOST` は、ホスト関数を呼ぶ前に `frame.pc` を更新しない。`CALL` と `CALL_INDIRECT` は `frame.pc = pc + Lowerer::WIDTH` を保存する。
- `execute_flat` は常に `pc = 0` から始まる。
- CRuby版の `--mir-profile` で `--disable-gems -e 'puts RUBY_DESCRIPTION'` の起動を数えると、実行したMIR命令は66,500,266、ホスト関数の呼び出しは15回だった。

### チェックポイントの位置（実装順1の計測）

CRuby版の `--mir-profile` で、ホスト呼び出しごとにその時点までの実行命令数を数えた。

| 呼び出し | `-e 'puts RUBY_DESCRIPTION'` | `/app/main.rb` |
|---|---:|---:|
| `clock_time_get`、`environ_*`、`args_*` | 52〜862 | 52〜862 |
| `fd_filestat_get`（fd 0、1、2） | 2,349〜2,630 | 2,349〜2,630 |
| `clock_time_get`、`random_get` | 15,401〜109,172 | 15,505〜109,302 |
| `fd_fdstat_get`（fd 0、1、2）、`fd_prestat_*` | 10,485,200〜13,379,615 | 10,477,565〜13,367,799 |
| 許可リストにない最初の呼び出し | `fd_write`：66,487,323 | `path_open`：20,511,642 |
| 終了時 | 66,500,266 | 66,015,244（最後の `fd_write`） |

`fd_filestat_get` は `ruby.c` の `fill_standard_fds` が標準入出力の有無を確かめる呼び出しで、Rubyは結果のうちエラーかどうかだけを見る。これを許可しないとチェックポイントが2,349命令目になるため、fd 0〜2に対するものに限って許可リストに加えた（後述）。

チェックポイントまでの割合は、`-e` で99.98%、スクリプトファイルで31%だった。スクリプトファイルでは `prism_script` がスクリプトを開いて構文解析した後に、prelude の読み込みなど残りの初期化を行う。スクリプトの内容が変わったときに変更後の内容で実行することを保つため、このチェックポイントの位置は変えない。`-e` の割合が半分を超えたので実装を進めた。

## 決定

ゲストがWASIのホスト関数を呼ぶ直前で実行状態を保存し、次回以降の起動でその時点から再開する。明示的に有効化したときだけ使う。

```sh
build/wardite --new-engine --mir-cache DIR --snapshot DIR -- ruby.wasm --disable-gems /app/main.rb
```

`--snapshot` は `--new-engine` と `--mir-cache` の両方を必要とする。Ruby APIは対象外とし、CLIだけで提供する。

### チェックポイントの位置

実行開始からのホスト呼び出しを順に見て、次の許可リストにない最初の呼び出しの直前をチェックポイントとする。

| 許可する呼び出し | 結果が何で決まるか |
|---|---|
| `args_sizes_get`、`args_get` | ゲストへ渡す引数 |
| `environ_sizes_get`、`environ_get` | ゲストへ渡す環境変数 |
| `fd_prestat_get`、`fd_prestat_dir_name` | preopenの一覧 |
| `fd_fdstat_get` | 標準入出力とpreopenの種別 |
| `fd_filestat_get`（fd 0〜2のみ） | 標準入出力の種別。時刻、サイズ、inodeは固定される |
| `clock_res_get`、`clock_time_get` | 時刻（固定される。後述） |
| `random_get` | 乱数（固定される。後述） |

許可リストの呼び出しは、ファイルの内容を読まず、fdを増減させず、出力もしない。許可リストにない呼び出し（`path_open`、`fd_read`、`fd_write`、`path_filestat_get` など）が現れた時点で、まだ実行していない状態を保存する。

許可リストにない呼び出しが一度もないまま終了した場合は保存しない。

### キー

次の値からSHA-256でファイル名を決める。1つでも異なれば別のスナップショットになる。

- Wasm全体のSHA-256
- MIR2キャッシュのキー（形式バージョン、生成コードの互換バージョン、最適化の無効化設定、ホスト識別子）
- スナップショットの形式バージョン
- ゲストへ渡す引数の列
- ゲストへ渡す環境変数の列
- preopenのゲスト側パスの列（順序を含む）
- fd 0、1、2それぞれの種別（`fd_fdstat_get` が返すfiletypeとflags）

引数がキーに入るため、`-e` のスクリプトが変われば別のスナップショットになる。スクリプトファイルを実行する場合は、パスが同じならファイルの内容が変わってもヒットする（ファイルを開くのはチェックポイントより後になる）。

### 保存する内容

[MIRCache](../../lib/wardite/efflorescence/mir_cache.rb) の `Writer` と `Reader` と同じ表現（little-endianの整数と長さ付きベクタ）を使う。Rubyの `Marshal` は使わない。

| 区分 | 内容 |
|---|---|
| ヘッダー | マジック、形式バージョン、キー、ペイロード長、ペイロードのSHA-256 |
| メモリ | 現在のページ数、64 KiBページごとの非ゼロのビット列、非ゼロのページの内容 |
| global | 各globalの値（レジスタと同じ整数表現） |
| フレーム | 下から順に、関数index、`pc`、レジスタ配列、ハンドラの深さの配列、戻り先レジスタ |
| WASI | 次に割り当てるfd番号 |

ホストのオブジェクト、開いているファイル、MIRの命令列は保存しない。命令列はMIR2キャッシュから読む。

tableとセグメントのdrop状態も保存しない。Efflorescenceは `table.set`、`table.grow`、`data.drop`、`elem.drop` などtableとセグメントを変更する命令を変換しないため、実行中も初期化直後の状態から変わらない。Wasm全体のSHA-256がキーに入るので、復元時に作るStoreの初期状態は保存時と同じになる。

次の場合は保存を取りやめ、通常の実行を続ける。

- いずれかのフレームの例外レジスタに値がある。
- ホスト関数からWasmへ再入している（公開呼び出しが入れ子になっている）。
- fdの表が、起動直後に作った状態（標準入出力とpreopen）から変わっている。
- ファイルの大きさが上限（256 MiB）を超える。

書き込みは、同じディレクトリの一時ファイルに書いてからrenameする。書き込みに失敗しても実行は続ける。

### 保存の実装

1. `execute_flat` の `CALL_HOST` で、ホスト関数を呼ぶ前に `frame.pc = pc` を保存する。ホスト呼び出しは起動全体で15回なので、実行ループへの影響は小さい。
2. `VM` が実行中のフレーム配列を参照できるようにする（`execute` が作る配列をインスタンス変数に持つ）。
3. `invoke_host` の直前で、スナップショットの記録が有効で、かつ呼び出すimportが許可リストにない場合に保存する。保存は1プロセスで1回だけ行い、以後は記録を無効にする。
4. 最上位フレームの再開位置は、ホスト関数を呼んだ命令の位置とする。`CALL_INDIRECT` も `frame.pc = pc` を保存し、呼び出し先を解決した後で命令幅だけ進める。このため、どちらの命令でもホスト関数の呼び出し中は `frame.pc` が命令の位置を指す。どちらの命令もホスト関数を呼ぶまでレジスタを書き換えないので、再実行できる。

### 復元の実装

1. Wasmのセクションを読み、MIR2キャッシュを読む。キャッシュがミスした場合はスナップショットを使わない。
2. スナップショットのファイルを読み、キー、長さ、ダイジェストを確かめる。
3. Storeを通常どおり作る（activeなdataとelementの配置を含む）。startセクションを持つモジュールでは、保存も復元も行わない。
4. メモリを保存時のページ数まで増やし、非ゼロのページを書き込み、それ以外のページを0にする。globalを設定する。
5. WASIを通常どおり初期化し、次に割り当てるfd番号が保存値と一致することを確かめる。
6. フレームを下から順に作る。各フレームは対象関数のプールから確保し、レジスタ、`pc`、ハンドラの深さ、戻り先レジスタを設定する。
7. `VM#resume` を追加し、`_start` を呼ぶ代わりに使う。最上位フレームの `pc` から `execute_flat` を始める。そのために `execute_flat` の開始位置を `frame.pc` から取るようにする（新規のフレームでは0）。
8. 終了コードと `proc_exit` の扱いは、`_start` を呼んだ場合と同じ経路を通す。

復元時の検査（関数indexの範囲、`pc` が命令幅の倍数で命令列の範囲内にあること、最上位フレームの `pc` がホスト関数を呼ぶ命令を指し、それ以外のフレームの `pc` の直前が呼び出し命令であること、レジスタ配列の長さが関数のレジスタ数と一致すること、ハンドラの範囲、戻り先レジスタの範囲）は、Storeを変更する前にすべて行う。1つでも失敗した場合は、作ったままのStoreで通常の起動に戻る。ここまでゲストの命令は実行していないので、副作用はない。

### 固定される値

チェックポイントより前に取得した時刻と乱数は、復元したすべての実行で同じ値になる。Rubyでは、初期化時に乱数から決めるハッシュのシードなどが実行ごとに変わらなくなる。

このため既定では無効とし、`--snapshot` を指定したときだけ使う。利用者向けドキュメントに、信頼できない入力をハッシュのキーとして扱う用途には向かないことを記載する。

### 不採用の案

- **引数に依存しないスナップショット**: `ruby_init` の直後で保存し、復元時に引数を差し替える方式。引数は `ruby_init` より前にゲストのメモリへ書き込まれるため、wasi-libcの内部構造に依存した書き換えが必要になる。採用しない。
- **ホスト呼び出しの記録と再検証**: チェックポイント前のホスト呼び出しの結果を記録し、復元時に再実行して比較する方式。キーに引数や環境変数を含めずに済むが、各呼び出しが書き込むメモリ範囲の記録と比較が必要で、実装が大きくなる。今回は採用しない。
- **Wizerの利用**: ゲストが初期化用の関数（`wizer.initialize`）をexportしていれば、Wizerで初期化済みのWasmを作れる。その場合Warditeの変更は不要になる。ただしRubyのビルドを変える必要があるため、このADRの対象（ゲストを変更しない）からは外れる。実装順の1の計測で効果が見込めない場合の代替とする。

## 検証

- スナップショットなし、保存する実行、復元する実行の3つで、標準出力と終了コードが一致する（[verify_ruby_wasm.rb](../../scripts/verify_ruby_wasm.rb) の3ケース。Wasmtimeとも照合する）。
- 引数、環境変数、preopenの一覧、標準出力の種別（端末とパイプ）のそれぞれを変えると、別のスナップショットになる。
- スクリプトファイルの内容を変えると、同じスナップショットから変更後の内容で実行される。
- WasmまたはMIR2キャッシュの互換バージョンを変えると、古いスナップショットを使わない。
- 切り詰め、ダイジェスト不一致、範囲外の関数index・`pc`・レジスタ数を、通常の起動へ戻して処理する。
- 保存を取りやめる4つの条件それぞれで、ファイルを作らずに実行が完了する。
- 2プロセスの同時保存と、書き込めないディレクトリで、実行結果が変わらない。
- 復元した実行で、`memory.grow`、例外処理、`call_indirect`、asyncifyによるunwindとrewindが動く（Rubyの `Fiber` と例外を使うスクリプトで確認する）。
- 小さいWasmのフィクスチャで、ホスト呼び出しの直前から再開したときに、その呼び出しの引数と結果が保存しない実行と一致する。

計測は、Ruby 4.0.9のWasmで、スナップショットなし（MIR2キャッシュのヒット）、保存する実行、復元する実行の3条件を各3回以上、別プロセスで行う。`load_from_buffer`、スナップショットの読み込み、ゲスト実行、プロセス全体、ピークRSS、ファイルサイズを記録する。

## 実装順

各行を独立したコミットにする。1の結果で先に進むかを判断する。

| 順 | 作業 | 確認 |
|---|---|---|
| 1 | チェックポイントの位置を計測する。ホスト呼び出しの名前と、その時点までの経過時間（CRuby版では `--mir-profile` の実行命令数も）を順に出力し、許可リストにない最初の呼び出しまでの割合を求める。`-e` とスクリプトファイルの両方で測る | 割合がゲスト実行時間の半分に満たない場合は中止し、結果をこのADRに追記する |
| 2 | `CALL_HOST` での `frame.pc` の保存と、`execute_flat` を `frame.pc` から始める変更 | 既存の試験とベンチマークが退行しない |
| 3 | スナップショットの書き込みと読み込み（ファイル形式、キー、検査） | 形式の往復と、破損時の扱いの試験が通る |
| 4 | 保存の契機と取りやめの条件 | 許可リストの判定と4つの条件の試験が通る |
| 5 | Storeの復元と `VM#resume`、CLIの `--snapshot` | 3ケースがWasmtimeと一致する |
| 6 | 計測とドキュメント | 3条件の計測結果と、固定される値の注意を記載する |

## 受け入れ条件

- Ruby 4.0.9のWasmで、復元する実行のプロセス全体が、スナップショットなしの実行より短いことを計測で示す。
- スナップショットを指定しない実行の時間と結果が、変更前から変わらない。
- [verify_ruby_wasm.rb](../../scripts/verify_ruby_wasm.rb) の3ケースが、保存する実行と復元する実行の両方でWasmtimeと一致する。
- CRubyのtest・型チェック・parityと、Spinelの回帰試験が通る。
