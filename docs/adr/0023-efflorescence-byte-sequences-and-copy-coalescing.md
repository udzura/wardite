# ADR 0023: バイト処理のMIR命令列を融合し、大きなループのCOPYを削減する

- **状態** 採用・実装済み。[PR #65](https://github.com/udzura/wardite/pull/65) でマージ（`8fe3c16`）
- **日付** 2026-11-19
- **比較基準** ADR 0021・0022を含むmain `76c2894`
- **関連** [ADR 0018（実ワークロードの計測）](0018-efflorescence-real-workload-measurement.md)、[ADR 0021（局所最適化の適用範囲）](0021-efflorescence-optimize-real-functions.md)、[ADR 0022（初回呼び出しでのMIR準備）](0022-efflorescence-lazy-function-build.md)

## 背景

4 MiBのBase64 encodeは比較基準のSpinel版で約564 ms、うちロードは約20 msだった。Time Profilerで取得した574サンプルのうち120が命令と先頭オペランドの取得・分岐、26が次のPCへの更新にあった。実行した約6,205万命令の86%は、encode関数内の1つの基本ブロックに集中していた。

decodeでは実行命令の99.98%が復号関数に集中した。1024×1024のRGB画像では、グレースケール変換が45%、Subフィルタ復元が31%、DEFLATE展開関数が22%を占めた。これらは動的なMIR命令数の割合である。PNG入力は全行にSubフィルタを使うfixtureで、出力はグレースケールのPGMである。

## 決定

### 4種類の命令列を1回でディスパッチする

レジスタ検証後、メモリを使う関数について連続する4命令を調べる。オペランドの依存関係まで一致したとき、先頭のopcodeを下表の融合命令に置き換える。関数名やゲスト内の関数番号には依存しない。

| 見つかった処理 | 元のMIR命令列（実行順） | 融合命令 | 大入力での実行回数 |
|---|---|---|---:|
| Base64 encodeの変換表から1文字読んで出力 | `I32_ADD → I32_LOAD8_U → I32_STORE8 → I32_ADD_IMM` | `I32_TABLE_STORE8` | 5,592,424 |
| Base64 decodeの入力バイトで復号表を引く | `I32_ADD_IMM → I32_LOAD8_U → I32_ADD → I64_LOAD8_U` | `I64_BYTE_LOOKUP` | 5,417,653 |
| RGBから輝度を求める重み付き加算 | `I32_ADD_IMM → I32_LOAD8_U → I32_MUL_IMM → I32_ADD` | `I32_BYTE_MUL_ADD` | 2,097,152 |
| PNG Subフィルタのバイト復元 | `I32_LOAD8_U → I32_ADD → I32_STORE8 → I32_ADD_IMM` | `I32_BYTE_ADD_STORE` | 3,145,728 |

各ハンドラは元の順序で演算、レジスタへの書き込み、メモリアクセスを行い、直前の結果を次の演算へ直接渡す。decodeの試作では、4命令をまとめるだけでディスパッチは25.6%減ったが、実時間はほぼ変わらなかった。中間値の再読み出しも省くと、同一バイナリの無効時と比べて11.5%短縮した。この結果を踏まえ、命令数に加えてプロセス全体の時間で採否を判断した。

元の4命令分のスロットを残すため、後続命令のPCは変わらない。列の途中に分岐先やcatchの入口があれば融合を見送る。decodeの2つのロードはオフセット0、重み付き加算はオフセット0の符号なしバイトロードと符号なし32ビットに収まる即値など、ハンドラが前提とする条件を照合する。[命令列の照合条件](../../lib/wardite/efflorescence/byte_sequences.rb)

### 大きな混合型ループには隣接COPYの統合を適用する

PNGのDEFLATE展開関数は2,616命令あり、ADR 0021の局所最適化の上限1,536命令を超える。そこで、上限を超えた関数でも、例外処理を含まず、呼び出しをまたがない長いループ（後方分岐の距離が64命令以上）があれば、既存のCOPY統合パスだけを実行する。

演算と直後のCOPYが同じ一時レジスタを介し、そのレジスタの定義と使用が関数全体で各1回、かつCOPYが基本ブロックの入口でなければ、演算結果をCOPYの宛先へ直接書く。全パスのサイズ上限を引き上げると、大きな関数の初回準備コストにも影響する。対象をこの線形パスに絞った試作で、PNG全体のCOPYは2,461,607回から214,483回に減り、全体時間も約2%短縮した。[適用範囲とCOPY統合の実装](../../lib/wardite/efflorescence/optimizer.rb)

## キャッシュ・計測への影響

- 4種類の融合は `--mir-disable superinstruction`、COPY統合は `--mir-disable copy` で個別に無効化できる。
- `--mir-profile` は融合列を1ディスパッチとして記録する。レジスタ読み出し回数から直接引き渡した分を差し引き、元の命令に対応する書き込みは数える。
- MIR2の `CODE_VERSION` を5から10に更新した。旧キャッシュは次のキャッシュ指定実行で再生成される。復元時にも4命令分の長さ、opcode、オペランドの依存関係および各命令のオペランドを検査する。

## 計測結果

Apple M3 Pro、Spinel `a2aa05227` の `-O2`、wardite-benches `f07c454` で計測した。キャッシュとプロファイルを無効にし、hyperfine 2.0.0で各バイナリを直接起動した。時間はウォームアップ2回後の9回の中央値（ms）。各セルは実行順を反転した2組の値を示す。iwasmとの倍率は同じ入力で別途ペア計測した実装後の時間を、iwasm 2.4.5 `--interp` の時間で割った値である。

|---|---:|---:|---:|---:|
| Base64 encode 4 MiB | 560.31 / 559.89 | 523.44 / 524.42 | 6.6% / 6.3% | 6.98 / 7.06倍 |
| Base64 decode 復号後4 MiB | 447.08 / 446.19 | 398.34 / 398.30 | 10.9% / 10.7% | 5.16 / 5.16倍 |
| PNG 1024×1024 | 382.00 / 383.22 | 337.16 / 336.62 | 11.7% / 12.2% | 5.64 / 5.72倍 |
| Base64 encode 256 KiB | 66.97 / 69.55 | 66.09 / 65.50 | 1.3% / 5.8% | 5.69 / 5.74倍 |
| Base64 decode 復号後256 KiB | 61.46 / 61.80 | 58.73 / 58.82 | 4.4% / 4.8% | 5.16 / 4.94倍 |
| PNG 256×256 | 94.78 / 93.36 | 93.03 / 92.06 | 1.8% / 1.4% | 7.14 / 6.97倍 |
